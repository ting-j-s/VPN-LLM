# Phase 6: Active Probe Resistance Gate

## 1. Purpose

Phase 6 introduces an active probe resistance evaluation module that tests
VPN-LLM server behavior under malformed or unexpected input. The goal is to
identify and eliminate stable, distinguishable error paths that could serve
as fingerprinting vectors — a technique documented in the OpenVPN active
probing literature.

This module:
- Defines 12 malformed-input probe scenarios
- Runs probes against a local server instance
- Measures response behavior variance (close timing, error types, timeout/response mix)
- Produces a report compatible with the Phase 4 DetectionGate / CountermeasurePolicy / LLM patch loop

## 2. Relationship to OpenVPN Active Probing

The OpenVPN fingerprinting paper demonstrates that active probes — sending
malformed or unexpected data to a VPN server and observing the response —
can distinguish between implementations. Key observable differences include:

| Behavior | Fingerprint Value |
|---|---|
| Immediate close vs. timeout | Distinguishes error-handling styles |
| Close timing variance | Creates stable timing signatures |
| Distinct error responses | Allows protocol-level fingerprinting |
| Response vs. silent drop | Indicates whether server validates input |

Phase 6 measures these behaviors locally and provides metrics to the LLM
patch loop for countermeasure generation.

## 3. Security: Local-Only Testing

**All probe payloads are for local controlled testing only.**

- `LocalSocketProbeRunner` **rejects** non-localhost targets (127.0.0.1, localhost, ::1)
- No third-party scanning functionality exists or is planned
- No probe scenarios target external services
- This module tests VPN-LLM's own server behavior, not remote services

## 4. Probe Scenarios

12 built-in scenarios cover common malformed input categories:

| # | Scenario | Input | Expected Policy |
|---|---|---|---|
| 1 | `empty_connection` | Connect, send nothing | Unified close after timeout |
| 2 | `one_zero` | Single zero byte | Silent close |
| 3 | `two_zero` | Two zero bytes | Silent close |
| 4 | `random_2k` | 2048 random bytes | Silent close |
| 5 | `short_frame_header` | Incomplete VTUN header | Silent close |
| 6 | `bad_magic` | Wrong magic bytes | Silent close |
| 7 | `invalid_frame_type` | Valid header, type=0xFF | Silent close |
| 8 | `bad_session_id` | Valid DATA, wrong session | Silent drop |
| 9 | `declared_length_too_large` | Length=1MB, data=9B | Silent close |
| 10 | `http_get_to_vpn_port` | HTTP GET request | Silent close, no HTTP response |
| 11 | `tls_clienthello_like` | Static TLS-like bytes | Silent close, no TLS response |
| 12 | `valid_heartbeat_wrong_session` | HEARTBEAT, wrong session | Silent drop |

## 6. Risk Rules

Risk score is a composite of:

| Component | Weight | What it measures |
|---|---|---|
| `distinct_error_types` ratio | 0.40 | How many different error behaviors |
| Timeout/response mixture | 0.30 | Whether some probes timeout, others respond |
| Close time spread | 0.30 | Normalized range of close timing |

Risk levels:
- **low** (< 0.3): Highly uniform behavior — all malformed inputs treated similarly
- **medium** (0.3-0.6): Some variance detectable
- **high** (> 0.6): Distinct, fingerprintable error paths

## 7. Integration with LLM Patch Loop

The probe report feeds into the existing Phase 4 detection pipeline:

```
probe report JSON
  → load_detection_report() → from_probe_report()
    → DetectionReport (metrics: probe_response_variance, malformed_close_time_variance)
      → evaluate_detection_report() with DetectionThresholds
        → suggest_countermeasures() from CountermeasurePolicy
          → build_adversarial_patch_prompt() → LLM prompt
```

Usage:

```bash
# Generate probe report
python3 -m src.evaluation.probe.report \
  --mock --output-json /tmp/probe.report.json

# Run through patch loop
python3 -m src.llm.detection.patch_loop \
  --user-request "reduce active probe fingerprint risk" \
  --report /tmp/probe.report.json \
  --output-prompt /tmp/probe_fix_prompt.txt \
  --output-json /tmp/probe_patch_loop.json
```

## 8. Countermeasure Recommendations

From `CountermeasurePolicy._HINT_MAP`:

### probe_response_variance (high)

- Unify timeout handling across all input types
- Implement silent drop for malformed frames
- Adopt constant close policy regardless of error type
- Avoid returning distinct error codes to remote peer

### malformed_close_time_variance (high)

- Use a single, unified close delay for all error types
- Implement uniform garbage-collection timeout
- Avoid immediate close for some errors and delayed close for others

## 9. Countermeasure Implementation (Planned)

To unify server error behavior:

1. **Silent drop**: Malformed frames → log internally, no response
2. **Constant close delay**: All error-triggered closes use the same delay
3. **Unified timeout**: Same timeout for all malformed input scenarios
4. **No application-layer response**: Never send error details to unauthenticated peers

These changes should be implemented in `server_core.py`'s transport-to-tun loop
and frame handling.

## 10. Current Limitations

1. **Mock runner only for tests** — Real probing requires a running local server
2. **No TCP RST detection** — Distinguishing FIN from RST requires raw socket or BPF
3. **Single connection per scenario** — Does not test concurrent probe patterns
4. **No timing precision calibration** — Close time measurements include Python socket overhead
5. **Does not test fragmentation reassembly edge cases** — Only basic malformed input
6. **Not a substitute for external security audit** — This is a controlled self-assessment tool
